이 문서는 2026-09-11 진행 중인 업데이트의 전환 준비안입니다. Production 조회·변경 권한을 부여하지 않습니다. 기존 `2026-2-production-cutover.md`는 **학기 전환** 절차이므로, 현재 학기의 사이트 업데이트에 그대로 실행하지 않습니다. 운영 상태를 확인하기 전에는 학기 전환이나 자료 복제가 필요하다고 가정하지 않습니다.

- 검증 대상: `westory-staging-177587430482`, Hosting `https://westory-staging-177587430482.firebaseapp.com`.
- 중간 소스: `96072114c16c102f372126e073addc7913c1f334`. 최종 후보 SHA와 독립 빌드 결과는 검증 완료 후 별도 고정합니다.
- 사용자가 요구한 기존 화면 구조와 기능을 유지합니다. 상단 메인 메뉴·떠 있는 왼쪽 보조 메뉴·중앙 로딩 표시, 빈칸 저장·정오답 효과·각주·링크·핵심포인트 보상은 출시 범위입니다. 교사용 수업 제시 화면과 판서는 제거 상태를 유지합니다.
- 운영의 현재 Hosting 서비스, 활성 학기, maintenance, 배포 revision, 자료 수량은 이번 실행에서 조회하지 않았습니다. 과거 문서의 값은 현재값으로 사용하지 않습니다.

## 승인 전 준비할 결과

1. 기능별 최신 증거와 미확인 범위를 하나의 판정표로 연결합니다. 실제 SDK·격리 React·실계정 화면 증거를 구분합니다.
2. 최종 소스에서 두 독립 빌드의 파일 hash가 일치하는지 확인하고 Staging 배포 파일과 대조합니다. Firebase Hosting 검증을 Vercel 검증으로 표현하지 않습니다.
3. 필수 업무·권한·재인증·동시 수정·기기별 화면을 확인합니다. 기존 44개 타입 기준선은 신규 진단 0과 구분하며, 출시 경로의 실제 장애는 남기지 않습니다.
4. Staging 합성 자료로 백업 hash·복원·이전 중단 후 재개·중복 입금 방지를 실증합니다. 실제 운영 백업 복구를 완료했다고 표현하지 않습니다.
5. 후보의 Functions·Rules·indexes·공개 설정·화면 조합과 변경 목록을 고정합니다. 서버 명령 목록은 이전 서버와 비교해 추출하며 일부 함수만 임의 선택하지 않습니다.

## 운영 승인 후 먼저 확인할 것

승인 요청에는 읽기 대상, 백업 저장 위치, 배포 대상, 자료 이전 범위, 업무 중단·재개 시각을 함께 제시합니다. 승인 전에는 아래 작업을 실행하지 않습니다.

| 확인 | 다음 행동을 결정하는 기준 |
| --- | --- |
| 프로젝트·실제 서비스·도메인 | `history-quiz-yongsin`과 본사이트의 실제 연결이 일치해야 합니다. Staging의 공개 설정·Maps 키를 운영에 복사하지 않습니다. |
| 활성 학기·명부·계정 | stable UID와 수강 등록 연결을 대조합니다. 테스트 학기나 합성 계정을 운영으로 복사하지 않습니다. |
| 기존 서버·Rules·클라이언트 | 현재 직접 쓰기와 새 Gateway 경계를 비교합니다. 구형 클라이언트를 차단할 서버 계약과 작업 중단 수단을 먼저 확인합니다. |

| 미완료 저장·업로드·평가 | 처리 중 명령·평가·출결·성적·파일을 보존합니다. 응답 미확인은 receipt로 판정한 뒤 재시도합니다. |

Wis 이전 adapter는 현재 **Staging/demo만 허용**합니다. 프로젝트 문자열만 바꿔 운영에 실행할 수 없습니다. 운영 현황·백업·예상 변경을 확인한 뒤, 승인 ID·프로젝트·원본 hash·버전·대상 UID를 검증하는 운영 실행 경계를 별도로 준비하고 재검증해야 합니다. 따라서 현재 구현을 운영 데이터 이전 실행 완료로 판정하지 않습니다.

## 백업과 적용 순서

1. 승인된 중단 창에서 신규 쓰기를 멈추고 진행 중 요청의 결과를 확인합니다. 단순한 학생 maintenance만으로 모든 교사·구형 클라이언트 쓰기가 차단됐다고 판단하지 않습니다.
2. Firestore export와 중요 컬렉션의 수량·hash, Storage 객체·checksum, Auth UID 목록의 비식별 hash, Functions revision·소스·환경 참조, Rules release, index 상태, 실제 프런트 배포본과 공개 설정 hash를 보관합니다. 비밀번호·토큰·secret 원문을 증거에 기록하지 않습니다.
3. 승인된 백업 저장소에서 복원할 정확한 위치와 방법을 확인합니다. 최신 운영 백업의 검증 실패 또는 보호할 원본의 누락이 있으면 중단합니다.
4. 필요한 additive index를 먼저 준비하고 READY 상태를 확인합니다. 서버·Rules의 호환 순서는 실제 운영 차이로 확정합니다. 새 서버와 구형 클라이언트가 함께 쓰는 구간을 허용하지 않습니다.
5. 데이터 이전이 필요한 경우만 대상별 dry-run/예상 변경을 고정합니다. 각 성공은 동일 commandId·payload와 marker로 이어가며, 순서가 바뀌거나 원본 hash가 달라지면 중단합니다. 학기 lifecycle/pointer는 업데이트 편의를 위해 바꾸지 않습니다.
6. 검증한 서버·Rules·프런트를 승인된 운영 대상으로 반영하고 실제 배포 hash를 대조합니다. Staging 합성 자료나 App Check debug 등록은 옮기지 않습니다.
7. 관리자·교사·학생의 로그인, 수업 저장/풀이/보상, 사전, 성적, 위스, 일정·출결 핵심 흐름을 확인합니다. 실제 사용자 알림은 승인된 대상과 내용에 한해서만 실행합니다.
8. 예상 변경과 실제 변경이 일치하고 필수 동작을 통과했을 때 승인된 절차로 접근을 재개합니다. 실패·미확인 요청이 남으면 재개하지 않습니다.

## 중단·복구 판단

| 발생 상황 | 복구 원칙 |
| --- | --- |
| 화면 문제, 새 데이터 쓰기 없음 | 새 서버 계약과 호환되는 고정 프런트로 복원하고 로그인·조회·저장을 확인합니다. |
| 권한 우회·다른 학생/학기 쓰기 | 쓰기를 차단하고 현재 상태와 receipt를 보존합니다. 기존보다 넓은 Rules로 우회하지 않습니다. |
| 이전 전 또는 commit 여부 미확인 | 원본과 marker·receipt를 대조합니다. 같은 요청을 확인하며 새 입금을 만들지 않습니다. |
| 이전 후 정상 활동이 존재 | 계좌·원장·감사 기록을 삭제하지 않습니다. 원래 opening과 후속 거래를 보존한 reconciliation/보상 계획으로 처리합니다. 프런트만 되돌려 해결됐다고 하지 않습니다. |
| 원본 유실·공식 성적 오연결·누계 불일치 | 영향 범위를 고정하고 검증된 백업 및 승인된 복원 절차를 사용합니다. 전체 restore는 다른 정상 쓰기까지 덮을 수 있으므로 별도 영향 검토가 필요합니다. |

9월 16일은 목표일입니다. 데이터 보호·권한·기존 업무 유지 조건을 낮춰 일정을 맞추지 않습니다. 운영 확인이 필요한 항목은 Staging 통과와 분리해 최종 승인안에 남깁니다.
