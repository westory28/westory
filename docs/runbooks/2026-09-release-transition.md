이 문서는 2026-09-12 기준 진행 중인 업데이트의 전환 준비안입니다. Production 조회·변경 권한을 부여하지 않습니다. 기존 `2026-2-production-cutover.md`는 **학기 전환** 절차이므로, 현재 학기의 사이트 업데이트에 그대로 실행하지 않습니다. 운영 상태를 확인하기 전에는 학기 전환이나 자료 복제가 필요하다고 가정하지 않습니다.

## 승인 전 준비할 결과

1. 기능별 최신 증거와 미확인 범위를 하나의 판정표로 연결합니다. 실제 SDK·격리 React·실계정 화면 증거를 구분합니다.
2. 최종 소스에서 두 독립 빌드의 파일 hash가 일치하는지 확인하고 Staging 배포 파일과 대조합니다. Firebase Hosting 검증을 Vercel 검증으로 표현하지 않습니다.
3. 필수 업무·권한·재인증·동시 수정·기기별 화면을 확인합니다. Batch11에서 기존 44개 타입 오류를 해결했고 허용 기준도 0으로 강화했습니다. 이후 변경에서도 오류 0을 유지하며, 출시 경로의 실제 장애는 남기지 않습니다.
4. Staging 합성 자료로 백업 hash·복원·이전 중단 후 재개·중복 입금 방지를 실증합니다. 실제 운영 백업 복구를 완료했다고 표현하지 않습니다.
5. 후보의 Functions·Rules·indexes·공개 설정·화면 조합과 변경 목록을 고정합니다. 서버 명령 목록은 이전 서버와 비교해 추출하며 일부 함수만 임의 선택하지 않습니다.

## 백업과 적용 순서

1. Root가 C 승인과 중단 창을 확인한 뒤 신규 쓰기를 멈추고 진행 중 요청의 결과를 확인합니다. 학생·교사·구형 클라이언트·직접 callable·Gateway·예약 작업/trigger/outbox·진행 중 업로드를 실제 차단/대기 대상별로 나눕니다. 단순한 학생 maintenance만으로 전체 차단됐다고 판단하지 않으며, 진행 중 명령은 receipt/marker와 대조해 완료·미실행·미확인을 기록합니다. drain 완료와 원본 hash 고정 전에는 이전하지 않습니다.
2. Firestore export와 중요 컬렉션의 수량·hash, Storage 객체·checksum, Auth UID 목록의 비식별 hash, Functions revision·소스·환경 참조, Rules release, index 상태, 실제 프런트 배포본과 공개 설정 hash를 보관합니다. 비밀번호·토큰·secret 원문을 증거에 기록하지 않습니다.
3. 승인된 백업 저장소에서 복원할 정확한 위치와 방법을 확인합니다. 중단 창 안의 일관된 최종 백업과 예상 변경 직전 hash를 대조합니다. 최신 운영 백업의 검증 실패 또는 보호할 원본의 누락이 있으면 Root가 쓰기 차단을 유지하고 중단 사실을 보고합니다.
4. 필요한 additive index를 먼저 준비하고 READY 상태를 확인합니다. 서버·Rules의 호환 순서는 실제 운영 차이로 확정합니다. 새 서버와 구형 클라이언트가 함께 쓰는 구간을 허용하지 않습니다.
5. 데이터 이전이 필요한 경우만 대상별 dry-run/예상 변경을 고정합니다. 각 성공은 동일 commandId·payload와 marker로 이어가며, 순서가 바뀌거나 원본 hash가 달라지면 중단합니다. 학기 lifecycle/pointer는 업데이트 편의를 위해 바꾸지 않습니다.
6. 검증한 서버·Rules·프런트를 승인된 운영 대상으로 반영하고 실제 배포 hash를 대조합니다. Staging 합성 자료나 App Check debug 등록은 옮기지 않습니다.
7. 관리자·교사·학생의 로그인, 수업 저장/풀이/보상, 사전, 성적, 위스, 일정·출결 핵심 흐름을 확인합니다. 실제 사용자 알림은 승인된 대상과 내용에 한해서만 실행합니다.
8. Root가 예상 변경·실제 변경 대조, 권한 없는 요청의 거부 검사, 로그인·핵심 업무 결과, 미확인 요청 0, 배포 artifact 일치를 기록한 뒤 승인된 절차로 접근을 재개합니다. 실패·미확인 요청이 남거나 중단 창을 넘기면 재개를 가정하지 않고 사용자에게 상태와 복구/연장 선택지를 보고합니다.

| 서버·Rules 배포 후, 데이터 변경 없음 | Root가 고정한 호환 조합으로 복원합니다. 이전 화면의 직접 쓰기가 새 경계와 충돌하면 프런트만 되돌리거나 Rules를 넓히지 않고 차단을 유지합니다. |
| 권한 우회·다른 학생/학기 쓰기 | 쓰기를 차단하고 현재 상태와 receipt를 보존합니다. 기존보다 넓은 Rules로 우회하지 않습니다. |
| 이전 전 또는 commit 여부 미확인 | 원본과 marker·receipt를 대조합니다. 같은 요청을 확인하며 새 입금을 만들지 않습니다. |
| 이전 후 정상 활동이 존재 | 계좌·원장·감사 기록을 삭제하지 않습니다. 원래 opening과 후속 거래를 보존한 reconciliation/보상 계획으로 처리합니다. 프런트만 되돌려 해결됐다고 하지 않습니다. |
| 원본 유실·공식 성적 오연결·누계 불일치 | 영향 범위를 고정하고 검증된 백업 및 승인된 복원 절차를 사용합니다. 전체 restore는 다른 정상 쓰기까지 덮을 수 있으므로 별도 영향 검토가 필요합니다. |

복구도 Root가 실행하고 사용자에게 결과를 보고합니다. C에서 승인된 복구 범위를 벗어나는 전체 restore·Auth 복구·정상 거래 조정은 영향 목록과 복원 목적지를 제시해 별도 승인을 받습니다. 재개 전에는 원장/성적/receipt 중복, 파일 참조, 승인 중간 상태 및 outbox 재발송 여부를 대조합니다. 개인정보·알림의 이미 발생한 외부 효과는 데이터 복원만으로 취소됐다고 기록하지 않습니다.

9월 16일은 목표일입니다. 데이터 보호·권한·기존 업무 유지 조건을 낮춰 일정을 맞추지 않습니다. 운영 확인이 필요한 항목은 Staging 통과와 분리해 최종 승인안에 남깁니다.
