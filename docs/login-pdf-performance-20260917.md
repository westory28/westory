## 로그인

점검 상태 확인 뒤 세션 생성(S)과 최종 사용자 서버 조회(P)를 동시에 실행한다. 기존 `M + S + P` 대기가 `M + max(S, P)`로 줄어든다. 두 확인이 성공해야 보호 화면을 연다. 기존 학생·교사 팝업 로그인에서는 이미 서버에서 확인한 점검 bootstrap 프로필을 재사용해 사용자 문서 중복 조회 1회를 제거했다.

실패·계정 변경·로그아웃 시 이전 인증 작업을 폐기한다. 재인증의 서버 읽기 확인과 점검 차단은 그대로 유지한다.

## PDF 업로드

- 원본과 페이지 이미지를 최대 3개씩 처리하고 페이지 순서는 유지한다. 일부 실패 시 이미 시작한 작업을 모두 기다린 뒤 재시도를 허용한다.
- 저장 작업의 학기 정보를 1회 조회해 공유한다. 서버는 준비·전송·최종 저장마다 동일 학기 revision을 검증한다.
- 같은 Blob을 해시 계산과 전송에서 다시 읽지 않는다.
- 서버는 받은 바이트의 SHA-256·파일 형식을 검증한 뒤 불변 Storage 객체를 저장하고, 객체 generation에 연결된 ticket을 VERIFIED로 확정해 응답한다. 정상 요청은 Storage 재다운로드와 별도 이벤트 대기를 하지 않는다.
- PDF 구조 추출은 기존 Storage 작업자가 백그라운드에서 계속 처리한다. ATTACHED 상태와 최신 추출 결과를 덮어쓰지 않는다.
- 기존 서버 응답과의 호환 경로는 1초 폴링 대신 서버 snapshot을 구독한다. 캐시·미확정 로컬 쓰기는 완료 근거로 사용하지 않는다.

## 검증

- `npm run build`, `npm run verify:typescript-baseline`(오류 0), `npm run format:check`, `npm --prefix functions run check` 통과.
- 실제 AuthContext/접근 경계와 합성 I/O를 이용한 브라우저 회귀 67개 통과. 세션과 프로필의 응답 순서 양쪽, 각각 실패, 진행 중 로그아웃을 포함한다.
- 로그인 bootstrap 검증 6개, 업로드 transport 38개, assets 22개, lesson management 30개 통과.
- 교사 저장 브라우저 회귀 7개 통과. 390/768/1440px에서 저장·실패·충돌·응답 유실 재시도·PDF 교체와 각주 삭제를 확인했다.
- 파일 6개에 각각 50ms 합성 지연을 준 비교 실행에서 직렬 359ms, 최대 3개 병렬 122ms였다. 실제 운영 업로드 속도 측정값이 아니다.
- 수정 전 운영의 기존 로그인 세션 복원은 1회 관측에서 앱 시작→레이아웃 준비 3.273초였다. Google 신규 로그인이나 학생 계정 측정값이 아니다.
- 운영 로그인 함수 로그에서 컨테이너 시작→준비에 약 1~2초가 걸리는 별도 원인을 확인했다. 상시 인스턴스는 추가 비용 선택 사항이며 코드 최적화와 구분한다.

실제 업로드 시간은 페이지 수·파일 크기·회선·서버 시작 상태에 따라 달라진다. 모든 로그인이나 업로드가 일정 시간 안에 끝난다고 보장하지 않는다.
