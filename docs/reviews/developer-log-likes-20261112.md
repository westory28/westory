# 개발자 일지 좋아요 권한 오류 수정

## 원인과 범위

기준 커밋은 `199bbe8daf0bc82bb31747deff010508372280ab`다. 배포 전 Firebase `history-quiz-yongsin`의 Firestore 규칙이 기준 소스와 일치함을 확인했다. 학생의 정상 좋아요 트랜잭션을 에뮬레이터에서 실행하면 본인 좋아요와 게시물 읽기는 성공하지만 쓰기에서 규칙의 1,000개 표현식 한도를 초과했다. 클라이언트에는 `permission-denied`로 나타났다.

조회수 변경 분기가 좋아요 변경에도 전체 접근 검사를 먼저 수행했고, 좋아요 수 변경과 본인 좋아요 문서 변경에도 동일한 검사가 반복됐다. 조회수 분기는 대상 필드부터 확인한다. 좋아요 수 분기는 본인 좋아요 문서의 변경 전후 존재 여부와 정확한 ±1 변경을 유지하고, 같은 원자적 요청에 반드시 포함되는 자식 문서 생성·삭제 규칙에서 전체 접근 검사를 수행한다.

좋아요 자식 문서는 학생 전용 접근 검사에서 기존 `isValidCompactStudentMaintenanceConfig`를 재사용한다. 점검 예외 20명에서도 계산 여유를 확보하며, 설정이 없을 때의 기본 허용과 설정 형식 검증·점검 활성화·예외 계정 검사는 유지한다. 학생 역할이 필수이므로 교사·직원 역할의 점검 통과 분기는 필요하지 않다. 전역 세션·점검 검사와 다른 기능의 규칙은 변경하지 않는다.

동시 요청에서는 미리 계산한 절대 좋아요 수가 먼저 저장된 다른 요청의 수와 충돌해 권한 검사에서 거부됐다. 같은 두 문서의 트랜잭션 읽기와 본인 좋아요 생성·삭제를 유지하면서 게시물 수를 서버 `increment(1/-1)`로 변경한다. 서버는 여전히 정확한 ±1만 허용하며, 경합 시 SDK의 트랜잭션 재시도로 본인 좋아요 상태를 다시 확인한다. 취소 시 0 아래로 내려가지 않도록 기존 0 처리도 보존한다.

현재 `site_settings/developer_logs/items/{id}`와 legacy `developer_logs/{id}`에 같은 수정을 적용한다. 본인 좋아요 생성·삭제의 학생 역할, 로그인 세션, 점검, 가입 승인 검사는 유지한다. 다른 사용자의 좋아요, 본문 변경, 좋아요 문서 없이 숫자만 바꾸는 요청은 허용하지 않는다. 자식 문서 규칙 또는 존재 상태 연계를 변경할 때에는 이 원자적 권한 계약을 함께 검토해야 한다.

기존 서비스의 오류 수정이다. 화면 디자인·Functions·Storage 규칙·AI 호출·외부 전송·개인정보 항목·학생 공개 범위는 변경하지 않는다. 운영 학생 데이터와 점수는 검증용으로 수정하지 않는다.

## 재현과 회귀 검사

- `npm run test:developer-log-likes-rules`: 실제 Firestore SDK 트랜잭션과 선행 읽기가 없는 직접 batch를 모두 사용한다. 현재·legacy 경로, 세션 정책 ENFORCE/OBSERVE_ONLY, 점검 예외 0/1/20명, 추가·취소·반복·동시 요청, 권한 없는 요청의 전체 실패를 검사한다.
- `DEVELOPER_LOG_LIKES_RULES_FILE`에 변경 전 규칙을 지정하고 실행기에 `--reproduce-baseline`을 넘기면 기존 정상 요청의 거부를 재현한다. 테스트는 고정된 `demo-westory-developer-log-likes` 프로젝트와 로컬 에뮬레이터 주소에서만 실행된다.
- `npm run test:score-request-rules`: 기존 성적 요청 권한 회귀를 유지한다. Firestore 배포 전 두 검사를 순서대로 실행한다.
- `npm run build`: 프런트엔드와 기존 빌드 전 검사를 확인한다.

경합이 없는 정상 좋아요 추가·취소는 SDK 문서 읽기 2회와 쓰기 2회다. 경합 시 SDK가 트랜잭션을 재시도하며 테스트는 시도별 요청과 성공한 커밋을 분리해 집계한다. 규칙 내부 읽기와 검증용 fixture 작업은 이 수치에 포함하지 않는다. 이번 수정은 클라이언트 조회 수를 줄였다는 의미가 아니다.

최종 좋아요 회귀는 150개 검사를 통과했다. 88개 정상 트랜잭션과 4개 직접 batch가 성공했고, 96개 권한 없는 요청은 부분 쓰기 없이 거부됐다. 해당 실행에서 트랜잭션은 거부·경합 재시도를 포함해 110회 시도, 220개 문서 읽기 요청, 192개 쓰기 준비, 176개 쓰기 커밋이었다. 직접 batch 60회는 120개 쓰기를 준비했고 8개만 커밋했다. 재시도 수는 실행별로 달라질 수 있다. 프런트엔드 최종 빌드와 기존 성적 요청 권한 검사도 통과했다.

## 운영 반영 확인

검증한 커밋을 main에 반영하고 Firestore 규칙만 선택 배포한다. 배포 후 Rules API의 활성 ruleset 소스를 검증한 파일과 대조한다. Vercel main 배포의 소스 커밋·Ready 상태와 운영 도메인 연결도 확인한다. 브라우저 확인은 지정된 `방재석` Chrome 프로필을 사용한다. 교사 세션의 화면 확인과 학생 권한의 에뮬레이터 검증은 구분하며, 실제 학생 계정의 운영 클릭으로 표현하지 않는다.
