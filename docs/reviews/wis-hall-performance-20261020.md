# 명예의 전당 조회 개선 (2026-10-20)

대시보드 순위 개선 후에도 명예의 전당은 기존 전체 계좌·학적 조회를 사용했다. 학생 화면은 잔액·원장·정책 조회 완료 후에, 교사 화면은 전체 학생·상품·주문 조회 완료 후에 명예의 전당 요청을 시작했다. 운영의 기존 `getWisEconomyState` POST 응답은 약 1.81~3.88초였다.

## 변경 계약

- 기존 `getWisRankingPreview`의 준비된 인스턴스를 재사용한다. 대시보드는 `ranking-preview`, 전체 명예의 전당은 `hall-of-fame` 요청으로 구분하며 동시 요청도 서로 섞지 않는다. 추가 상시 인스턴스, keepalive, 폴링, 자동 재시도는 없다.
- 현재 학기는 `semester_wis_preview_entries`의 작은 순위 자료를 학기별로 한 번 읽는다. 학생은 자신의 정식 학년으로 제한한다. 최대 2,000명이며 초과하면 실패한다. 전체 계좌의 원장이나 전체 학생의 학적을 읽지 않는다.
- 서버에서 공개될 학년·학급 후보를 고른 뒤, 그 후보의 현재 계좌·학적·학급을 확인한다. 계좌는 순위 필드만 선택해 긴 거래 내역을 전송하지 않는다. 점수 하락·학적 이동·삭제로 다음 후보가 필요하면 아직 확인하지 않은 후보만 추가 확인한다. 한 요청에서 문서 조회와 후보 검증을 공유하며 반복의 상한은 2,000명이다.
- 최종 공개 후보의 프로필만 읽고 같은 응답의 최신 등급 정책으로 이모지를 결정한다. 학생의 별도 정책 요청을 없앤다. 잔액·원장·원본 UID·전체 계좌를 응답하지 않는다.
- 학년·학급별 공개 인원, 공동순위의 20명 상한, 0점 보충, 테스트 계정 제외를 유지한다. 학생은 본인 학년과 학급만 받는다. 교사의 명시적 보관 학기 조회는 당시 계좌 학적을 사용하며 현재 학적 인덱스로 대체하지 않는다.
- 명예의 전당은 다른 포인트 탭의 금융·상점 조회와 독립적으로 시작한다. 다른 탭을 처음 열면 기존 조회를 수행한다. 계정·인증 세대·학기 변경 시 이전 응답은 버린다. 순위 이름이나 정책을 브라우저에 저장하지 않는다.

## 검증 및 배포

- `node scripts/verify-wis-ranking-preview.mjs`: 단일 인증 요청, 전체 Hall·5명 미리보기 분리, 정책 중복 조회 제거, 계정·인증 epoch·학기 변경, 동시 요청과 명시적 재시도.
- `node scripts/verify-wis-hall-loading.mjs`: 실제 부모 페이지의 hook/effect를 실행해 직접 진입, 다른 탭 지연 로딩, 늦은 응답, 오류 복구와 보관 상점 경계를 검사한다.
- `node functions/scripts/verify-wis-hall-index.cjs`: 전체 Hall 회귀 16개. 기존 공개 결과 동등성, 후보 재배치·보충, 학생 범위, 공동순위·0점·프로필·보관 조회, 실제 adapter 필드 선택과 기존 읽기 불변성을 검사한다. 321명 합성 자료의 전체 교사 Hall 처리 CPU는 로컬 약 60~70ms였다. 이는 운영 네트워크 지연 실측이 아니다.
- 독립 감사에서 학년·학급 공개 한도 4/10/20, 공동순위 켜짐/꺼짐, 점수 하락·이동·탈퇴를 섞은 36가지 결과를 기존 전체 조회와 비교했다. 실제 필드 제거를 모사한 학생·교사·보관 조회도 일치했다.
- `npm run build`, `npm --prefix functions run check`를 배포 전 필수로 수행한다. 운영 인덱스의 현재 학기 조회는 학생·교사 조건 모두 추가 인덱스 없이 실행되는 것을 읽기 전용으로 확인했다.

기존 서울 `getWisEconomyState`와 다른 금융 명령 함수는 배포 대상이 아니다. Firebase 대상은 `getWisRankingPreview` 하나이며, 별도 인덱스나 규칙 변경은 없다. 프런트엔드 main 배포와 Vercel 승격 후 로그인한 운영 화면의 `data-hall-load-ms`, 전체/학급 전환, 콘솔 오류를 확인한다. 이 DOM 속성은 로컬 측정값이며 저장하거나 서버로 전송하지 않는다. 준비된 인스턴스를 재사용해도 배포 직후 초기화·플랫폼 재시작·네트워크 상황까지 1초를 보장할 수는 없다.
